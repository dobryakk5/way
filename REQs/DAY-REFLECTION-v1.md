# DAY-REFLECTION v1 — итог дня для игрока

Day Reflection не является новым игровым или диагностическим движком. Это детерминированная проекция уже доказанных событий текущего дня в понятный игроку ответ: что изменилось, что пока не завершено и что игра уже может осторожно сказать о его способе действовать.

Статус: **реализовано**. CONTENT_VERSION `mvp-v2.5-alpha.2`, GAME_STATE_VERSION 5, алгоритм профиля `2`, scoring `contrast`. Раздел 6.3 (отклик по действиям дня) закрывает ранние дни, когда профиль ещё ничего не может сказать; раздел 11 — измерения на 300 полных прохождениях.

## 1. Решение и границы

| Решение | Обоснование |
|---|---|
| Итог собирается на клиенте чистой функцией `buildDaySummary(state, content)` в конце `prepareEvening` (`src/engine/day.ts`) и хранится в `GameState.nights[].summary` | Effects, facts, traces, opportunities и `heroDevelopmentProfile.eveningSnapshots` существуют только в клиентском движке. Сервер хранит сырые `CHOICE_MADE` и SQL-агрегат evidence; методологических порогов у него нет, `profile_status` он не меняет (`reports/CHARACTER-STATE-PERSISTENCE-v2.1-IMPLEMENTATION.md`, «Methodology boundary») |
| Серверная схема и API не меняются | Копия итога, посчитанная клиентом, не стала бы авторитетной: сервер не может ни пересчитать её, ни проверить. Revision у такой таблицы ничего бы не гарантировал |
| Новых диагностических сущностей и весов нет | `LogicVector` неотрицателен и нормирован; «свидетельство против типа» через отрицательный вес запрещено методологией |
| `buildDaySummary` живёт в `src/engine/` без DOM, React и `Math.random` | Позже тот же модуль можно запустить на сервере вместе с перенесённым движком (раздел 12) |

## 2. Принцип «ничего не придумывает»

Каждая строка итога несёт `source` — ссылку на запись, которая её доказывает. Строка без источника недопустима: валидатор контента и тесты её отвергают. Итог выбирает материал только из:

- `history` дня (выбор: `cardId`, `choiceId`, `day`, `slot`);
- `observations` дня (`trace`, `opportunity`, `variant`);
- `journal` дня (`kind: 'insight'`);
- `scheduled` (отложенные цепочки);
- `opportunityState` и `facts`;
- `heroDevelopmentProfile.eveningSnapshots` за этот день.

## 3. Модель

```ts
type SummarySource =
  | { kind: 'choice'; day: number; slot: number; cardId: string; choiceId: string }
  | { kind: 'observation'; day: number; slot: number; observationKind: 'trace' | 'opportunity' | 'variant'; id: string }
  | { kind: 'insight'; day: number; id: string }
  | { kind: 'scheduled'; cardId: string; day: number; latestDay?: number }
  | { kind: 'exposure'; day: number; opportunityId: string }   // opportunity показана сегодня
  | { kind: 'snapshot'; day: number };

interface DaySummary {
  schema: 1;
  day: number;
  contentVersion: string;
  rulesVersion: string;                 // версия правил и шаблонов итога
  profileAlgorithmVersion: string;      // = state.heroDevelopmentProfile.algorithmVersion
  worldChanges: { source: SummarySource; templateId: string; text: string }[];
  unfinished: { threadId: string; source: SummarySource; promise: 'firm' | 'soft'; templateId: string; text: string }[];
  reflection: {
    status: ProfileStatus;              // 'insufficient' | 'provisional' | 'stable'
    previousStatus?: ProfileStatus;     // статус snapshot предыдущего вечера
    previousCandidate?: ActionLogic;    // snapshot.candidatePrimary предыдущего вечера
    coverage: number;
    candidate?: ActionLogic;            // snapshot.candidatePrimary
    observed?: ActionLogic;             // snapshot.observedPrimary, только при stable
    case: 'downgrade' | 'refining' | 'provisional' | 'forming' | 'just_started' | 'stable' | 'unsettled';
    templateId: string;
    text: string;
    echo?: {                              // раздел 6.3
      kind: 'repeat' | 'varied'; observationId?: string;
      sources: { kind: 'choice'; day: number; slot: number; cardId: string; choiceId: string }[];   // ≥ 2
      templateId: string; text: string;
    };
    // Отдельное сообщение: не конкурирует с выбором шаблона выше.
    transition?: { arcId: string; text: string };   // development.transitions[] этого дня
  };
}
```

- Хранится в `nights[i].summary?` (поле опциональное). `primary` и `note` остаются как есть: на них опираются журнал и автопереход.
- `profileAlgorithmVersion` берётся из прохождения (`state.heroDevelopmentProfile.algorithmVersion`). `content.profile.currentAlgorithmVersion` — выбор для новых прохождений, у старого героя версия другая.
- Отдельного поля `coverageLevel` нет: подпись уровня получает UI из `status` (раздел 6).

## 4. Правила отбора

### 4.1 Что изменилось (`worldChanges`)

По конечному значению факта изменение за день не выводится: снимка фактов на начало дня в состоянии нет, а `history` хранит только `cardId/choiceId`. Поэтому пункт появляется только если установку факта доказывает запись этого дня:

1. выбор из `history` дня, чьё `choice.effects.setFacts` содержит факт (эффекты берутся из контента: `choiceById(card, choiceId)`, `src/engine/variants.ts`; id выборов в карточке уникальны по всем `choiceVariants`, проверено — неоднозначных нет);
2. `observation` дня (`trace`, `variant`, `opportunity`);
3. `insight` дня (`journal`).

Формулировка факта — «стало X». Предыдущее значение («было Y») не выводится никогда.

Отбор: шаблону задаётся `priority`. В итог берутся до трёх пунктов с наибольшим приоритетом (при равенстве — более поздний `slot`), показываются в порядке `slot`. Изменения ресурсов и качеств сами по себе пункта не порождают.

### 4.2 Что не завершено (`unfinished`)

Только по реестру нитей (раздел 5). Обещание конкретного продолжения допустимо, только если оно гарантировано движком:

- `firm` — только для цепочки, которая лежит в `state.scheduled`, у которой `card.required === true` и задан `latestDay`. Движок бросает `Missed required chain` (`src/engine/day.ts:25`), если такая цепочка не показана к `latestDay`; значит обещание не может остаться невыполненным.
- Слово «завтра» допустимо, только если `scheduled.day === state.day + 1`. Иначе — «в ближайшие дни» без даты.
- `soft` — все остальные случаи («это ещё может вернуться»): цепочка без `required`, нить по значению факта без `followUp`, открытая opportunity.

Одно изменение ресурса или отношения обещания не порождает.

### 4.3 Что игра уже может сказать (`reflection`)

Источник — `eveningSnapshots.find(s => s.day === day)`. Если snapshot отсутствует, это ошибка сборки итога, а не повод считать профиль заново.

## 5. Нити — контентный реестр

Новое состояние в `GameState` не появляется. В `GameContent` добавлено `threads` (`src/content/data/threads.json`):

```ts
type ThreadStage = 'dormant' | 'open' | 'resolved' | 'abandoned';
interface ThreadFollowUp { cardId: string; firmTexts: string[]; tomorrowTexts?: string[] }

type ThreadDefinition =
  | { id; kind: 'fact'; fact: string; stages: Record<FactValue, ThreadStage>; texts: { open: string[] }; followUp?: ThreadFollowUp }
  | { id; kind: 'opportunity'; opportunityId: string; texts: { open: string[]; resolved: string[]; abandoned: string[] } }
  | { id; kind: 'chain'; texts: string[]; followUp: ThreadFollowUp };   // цепочка без своего факта
```

- `fact`: нить открыта, пока значение факта отображается в стадию `open`. Стадии `resolved` / `abandoned` разрешены, но молчат: итог о них не говорит.
- `opportunity`: соответствие фиксировано: `opportunityState` open → open, taken → resolved, expired → abandoned. Факта у нити нет, тексты лежат в самой нити. Рассказывается только то, что случилось **сегодня**: показана сегодня (`opportunityExposure.day`), принята сегодня (выбор, который ставит `resolvedFact = takenValue`), истекла сегодня (observation `opportunity`).
- `chain`: для обязательных и необязательных цепочек, которых не обслуживает ни один факт.
- `followUp` сам по себе `firm` не гарантирует (см. 4.2). У `ThreadDefinition` нет поля `promise`: обещание доказывает состояние прохождения.

Когда нить попадает в `unfinished`: только в вечер, когда она была открыта (факт установлен выбором дня, цепочка запланирована выбором дня, opportunity показана сегодня), и, для `firm`, ещё в вечер перед днём цепочки (`scheduled.day === day + 1`). Нить не повторяется каждый вечер.

Валидатор (`summaryErrors`, `scripts/check-content.ts`; схемы — `scripts/schema.ts`):

- `stages` покрывают **ровно** значения `FactDefinition.values`, начальное значение — `dormant`, каждое значение не-`dormant` достижимо хотя бы одним выбором, есть хотя бы одна `open`-стадия;
- нить `kind: 'fact'` запрещена на факте, который является `resolvedFact` какой-либо opportunity (иначе одно событие попало бы в итог дважды): `liaison.martaHelp`, `market.window`, `rest.beforeFair`, `ilya.meeting`;
- одна карточка `followUp` принадлежит одной нити, одна opportunity — одной нити;
- у `followUp` на `required`-карточку обязательны `firmTexts`, и некий выбор обязан планировать её с `latestDay`; у необязательной карточки `firmTexts` и `tomorrowTexts` должны быть пустыми;
- `firmTexts` и все мягкие тексты не называют день (`завтра`, `послезавтра`, `сегодня`), `tomorrowTexts` обязаны сказать «завтра»;
- карточка, на которую указывает `followUp`, существует и кем-то планируется; для `kind: 'chain'` её тип — `chain`.

## 6. Отражение профиля (UX)

Точки и «пять этапов» не показываются: в игре нет пяти этапов диагностики. Показатель уверенности (`confidence`) в UI не выводится, полоса — по `coverage`. Подпись уровня UI выводит из `status`: `insufficient` → «Первые наблюдения», `provisional` → «Картина складывается», `stable` → «Есть устойчивая гипотеза».

### 6.1 Выбор шаблона

Игра ничего не обещает по номеру дня: правило зависит только от двух вечерних snapshot (`S` — этого вечера, `P` — предыдущего, если он есть). На одном прохождении кандидат появится раньше, на другом позже. Берётся **первый** подходящий случай:

| № | Условие | Шаблон | Содержание |
|---|---|---|---|
| 1 | `P.status === 'stable'` и `S.status !== 'stable'` | `reflection.downgrade` | «Картина снова стала менее определённой — последние решения не повторили прежний способ действовать.» |
| 2 | `S.status === 'provisional'` и `P.candidatePrimary` задан и `P.candidatePrimary !== S.candidatePrimary` (кандидат сменился или пропал) | `reflection.refining` | «Картина уточняется. Последние решения показали другой способ действовать, поэтому мы пока не спешим с выводом.» Без названия прежнего и нового кандидата |
| 3 | `S.status === 'provisional'` и `S.candidatePrimary` задан | `reflection.provisional.<logic>` | осторожное содержательное наблюдение о действиях (6.2) |
| 4 | `S.status === 'provisional'`, кандидата нет | `reflection.forming` | «В нескольких разных ситуациях начинает повторяться похожий способ действия. Мы продолжаем наблюдать.» |
| 5 | `S.status === 'insufficient'` | `reflection.just_started` | «Мы начали замечать твои решения. Пока слишком рано говорить о повторяющемся способе действия.» |
| 6 | `S.status === 'stable'` | `reflection.stable.<logic>` | содержательное отражение по `observedPrimary` |

Так игра не выглядит как тест, который каждый день «переобувается»: смена кандидата никогда не превращается в противоположное утверждение.

Уточнения:

- Случай 2 действует **только пока `S.status === 'provisional'`**. При `stable` кандидат технически может смениться или пропасть, но обычное устойчивое отражение (случай 6) он перехватывать не вправе.
- В случае 2 считаются и смена (`expert → achiever`), и пропажа (`expert → нет кандидата`), но не появление первого кандидата (`нет → expert`): это обычный случай 3.

Дополнительно:

- **Последний день эпизода без `stable`**: вместо случая 3–5 берётся `reflection.unsettled` — «Способ действовать пока не сложился в одну линию — это тоже результат.»
- **Переход стадии** (`development.transitions[]` за этот день) показывается **отдельным** сообщением `reflection.transition` (`arcId` и `promotionText` дуги, как в `eveningText`) и не участвует в выборе шаблона выше.

### 6.2 Тексты по логикам

Для каждой из восьми `ActionLogic` (`opportunist`, `diplomat`, `expert`, `achiever`, `individualist`, `strategist`, `alchemist`, `ironic`) пишутся **два отдельных** авторских текста:

- `provisional` — описывает фактический паттерн действий: «В нескольких ситуациях ты сначала… Посмотрим, повторится ли это.» Без «обычно», без «ты такой», без названия логики или стадии;
- `stable` — допускает обобщённое отражение: «Сейчас герой чаще опирается на…».

Тексты не копируют друг друга; валидатор проверяет, что у каждой логики есть оба и что они различаются.

**Смысловое правило.** До `stable` текст описывает повторившиеся действия в конкретных ситуациях, но не устойчивое свойство человека.

- Допустимо: «В нескольких ситуациях ты сначала пытался разобраться, а потом действовал.»
- Недопустимо: «Ты предпочитаешь сначала разобраться.», «Тебе свойственно…», «Для тебя главное…», «Ты склонен…», «Ты обычно…», «Ты всегда…».

Смысловое правило проверяется двумя способами. Структурно: каждый `provisional`-текст начинается с «В нескольких ситуациях ты » и содержит оговорку «Посмотрим». Стоп-списком (`PERSONAL_TRAIT_PATTERN` в `scripts/check-content.ts`: «обычно», «всегда», «никогда», «ты такой», «ты из тех», «по натуре», «свойственн-», «склонен», «предпочита-», «для тебя главн-», «тебе важно», «ты —») по всем `reflection.*`, кроме `reflection.stable.*`. Стоп-список лишь страховка: решает смысл, и новые тексты проверяются редактором.

### 6.3 Отклик по действиям дня (`echo`)

Профиль не отвечает на вопрос «игра видит мои решения» раньше 7–8-го дня (раздел 11). Поэтому рядом с отражением профиля стоит отклик, который **не является выводом о человеке** и не читает профиль вообще: это буквальное описание того, какими были действия этого дня.

- **Источник.** Авторская характеристика конкретного действия: `summaryTemplates.observed["cardId/choiceId"] = observationId`, словарь `summaryTemplates.observations[] = { id, text }`. Текст завершает фразу «Сегодня в нескольких ситуациях ты …» и описывает поступок («сначала старался разобраться, как всё устроено», «шёл к срокам и результату»). Идентификаторы называются по поступку, не по стадии (`check_how_it_works`, `protect_own_side`, `look_after_relationship`, …); валидатор отвергает идентификатор с названием логики. На выбор приходится не больше одной характеристики. Не из вектора `diagnosticAction`: иначе получился бы второй слабый диагностический алгоритм.
- **Почему реестр, а не поле в карточке.** Показанная пара выборов хранится в сохранении и сверяется с контентом побайтно (`canonical`) по строгой схеме выбора; новое поле в карточке сделало бы такие сохранения «повреждёнными». Реестр хранит ту же авторскую характеристику, но не трогает ни карточки, ни показанные пары.
- **Правило.** Нужны хотя бы два размеченных решения за день. Два и больше с одной характеристикой (решения разных слотов) → `repeat`: «Сегодня в нескольких ситуациях ты {действие}. Это ещё не вывод — посмотрим, повторится ли это в других обстоятельствах.» При нескольких повторах побеждает самый частый, при равенстве — более поздний, затем по id. Размеченные решения все разные → `varied`: «Сегодня твои решения были разными — общего рисунка за этот день пока не видно.» Одно размеченное решение или ни одного → отклика нет.
- **Где показывается.** Когда профилю нечего сказать по существу: случаи `just_started`, `forming`, `refining`, `downgrade`, `unsettled`. При `provisional` с кандидатом и при `stable` отклика нет: они говорят сами. Правило не привязано к номеру дня: если сроки появления кандидата изменятся, отклик продолжит работать.
- **Доказуемость.** `echo.sources` — выборы этого дня из `history`; загрузчик сохранения проверяет, что они существуют, относятся к этому дню и стоят в разных слотах, и не принимает `repeat` без `observationId`.
- **Граница.** Для отклика нет весов, порогов и вывода о способе действовать. Для текстов действует смысловое правило 6.2 (стоп-список `PERSONAL_TRAIT_PATTERN`, обращение «ты» запрещено внутри текста характеристики).

Три глубины «что мы заметили»: сегодняшние действия (`echo`) → позже осторожное наблюдение по кандидату → ещё позже устойчивое отражение.

## 7. Детерминированность

Выбор варианта формулировки — через существующий `hashSeed(seed, runId, day, templateGroup, rulesVersion)` (`src/engine/rng.ts:1`), не через `Math.random`. Итог строится один раз: `prepareEvening` уже защищён флагом `preparedEveningDay`, повторный вызов на том же вечере состояния не меняет. После построения итог заморожен.

## 8. Итог — только проекция

`nights[].summary` ни движок, ни `prepareEvening`, ни условия контента, ни выбор сцен, ни профиль не читают. Иначе замороженный текст стал бы скрытым входом в расчёты. Тест: состояние после `leaveEvening` побайтно одинаково с `summary` и без него (кроме самого поля).

## 9. Экран

- `EveningScreen` (`src/ui/screens/EveningScreen.tsx`): если у дня есть `summary`, автопереход отключается, вместо него явная кнопка «День N+1» / «Эпилог». Длительность автоперехода под объём текста не подгоняется: часть игроков не успеет прочитать.
- Для дней без `summary` (старые сохранения) — прежнее поведение с `primary`.
- `JournalScreen` показывает итог дня рядом с `night.primary`.
- Блок «Сохраняем день…» (`blocked`) остаётся без изменений.

## 10. Версии и сохранения

- `GAME_STATE_VERSION` остаётся 5: `summary` опциональное и backward-compatible. Подъём до 6 откат релиза не чинит: у старой сборки `version: z.literal(5)`, версия 6 ей так же незнакома.
- `CONTENT_VERSION` поднимается (`mvp-v2.5-alpha.1` → `mvp-v2.5-alpha.2`), так как поставка меняет контракт контента (`threads`, шаблоны итогов). Но схема игры требует `contentVersion: z.literal(CONTENT_VERSION)` (`src/persistence/save.ts:98`), поэтому подъём без миграции превратит **каждое** текущее сохранение v5 в «повреждённое». Обязательно: аддитивная нормализация в `migrateSave` по образцу `normalizeDevelopmentV5` — v5 с `alpha.1` принимается, `contentVersion` переписывается, остальное состояние не трогается; оригинал архивируется существующим механизмом `legacy-…` в `loadSave`.
- **Связка, не замеченная в первой версии ТЗ.** Доказательства профиля проверяются на равенство `evidence.contentVersion === state.contentVersion` (`heroDevelopmentProfile.ts`, проверка доказательств). Подъём версии без поправки сделал бы невалидными все сохранения с доказательствами. Поэтому `src/content/version.ts` объявляет `COMPATIBLE_CONTENT_VERSIONS = ['mvp-v2.5-alpha.1']` (версии с теми же карточками, выборами и оценкой): их доказательства остаются верными «как записаны», а `normalizeDevelopmentV5` переписывает только `game.contentVersion`. Следующая версия контента, меняющая карточки или оценку, **не** добавляется в этот список.
- Схема `nights` (`save.ts`) получает `summary` внутри `.strict()`. Загрузка валидирует: `summary.day === night.day`; каждый `source.kind === 'choice'` существует в `history`; `profileAlgorithmVersion` совпадает с `heroDevelopmentProfile.algorithmVersion`. Проверяется и согласованность с вечерним snapshot того же дня (`status`, `coverage`, `candidate`, `observed`); источники `choice`, `observation`, `insight`, `exposure` ищутся в самом сохранении, `scheduled` — как существующая карточка в будущем. Подделанный итог отклоняется, как подделанные проценты профиля в v2.4.
- Что делает загрузчик при ошибке схемы: `loadSave` возвращает `damaged`, а `useGameStore` показывает «Сохранение повреждено или относится к другой версии. Исходная запись сохранена.» (`useGameStore.ts:126`); запись не стирается.
- Итоги за ранее сыгранные дни задним числом не пересчитываются.

## 12. Серверный этап (не входит в v1)

Когда движок будет перенесён на сервер, появится `day_summaries`:

```
character_id, game_day, revision, is_current,
content_version, rules_version, profile_algorithm_version,
last_seq, payload jsonb, supersedes_id, created_at
UNIQUE (character_id, game_day, revision)
```

Сервер прогонит тот же `buildDaySummary` над воспроизведённым состоянием; исправление ошибки создаёт новую revision (`is_current`), прежняя остаётся в истории. Там же стоит закрыть расхождение: на сервере в CHECK профиля есть `transition` (`001_…sql`), на клиенте `ProfileStatus = insufficient | provisional | stable`, а переходы живут в `development.transitions`.

## 13. Известные ограничения

- Итог живёт только в локальном сохранении клиента: при смене устройства или очистке хранилища он пропадёт, сервер его не восстановит.
- Сборка, выпущенная до этой поставки (откат релиза, старая вкладка PWA), считает новое сохранение «другой версии» и не загружает его; запись при этом не стирается.
- За дни, сыгранные до поставки, итогов нет.
- «Было Y, стало X» для фактов не выводится; только «стало X».
- Центр у смешанного героя может не сложиться до конца эпизода; для этого есть отдельный шаблон.
- Нити без `followUp` дают только мягкие формулировки.
- Профиль не отвечает на вопрос «что игра заметила» раньше 7–8-го дня; до этого отвечает только отклик по действиям (6.3). Отклик пока отсутствует в сценах, у которых нет разметки (6-й день, поздние свободные слоты; раздел 11).
- Авторская разметка 250 выборов (`summaryTemplates.observed`) и тексты 12 характеристик — первая редакция, без независимой вычитки редактором. Одну и ту же характеристику «держался порядка» или «не усложнял» читатель может понять по-разному; её стоит проверить на живых игроках.
- Слово «завтра» в итоге относится к вечеру того дня; в журнале оно стоит под заголовком своего дня.

## Приложение А — эталонные тексты

- `insufficient`: «Мы начали замечать твои решения. Пока слишком рано говорить о повторяющемся способе действия.»
- `provisional`: «В нескольких разных ситуациях начинает повторяться похожий способ действия. Мы продолжаем наблюдать.»
- Подписи уровней: «Первые наблюдения» → «Картина складывается» → «Есть устойчивая гипотеза».
- Откат: «Картина снова стала менее определённой — последние решения не повторили прежний способ действовать.»
- Смена кандидата: «Картина уточняется. Последние решения показали другой способ действовать, поэтому мы пока не спешим с выводом.»
- `provisional`, эксперт (образец): «В нескольких ситуациях ты сначала старался разобраться, как всё устроено, и только потом действовал. Посмотрим, повторится ли это.»
- `stable`, эксперт (образец): «Сейчас герой чаще опирается на понимание устройства дела и собственную компетентность…»
- Тексты всех восьми логик и шаблоны изменений и нитей лежат в `src/content/data/summary-templates.json` и `threads.json`. Это первая авторская редакция по рубрике логик (`ProfileAlgorithmConfig.rubric`) и по самим карточкам; редакторской вычитки (как у разметки диагностики) они ещё не проходили.
- Отклик, `repeat`: «Сегодня в нескольких ситуациях ты в первую очередь берёг свои силы, границы и интерес. Это ещё не вывод — посмотрим, повторится ли это в других обстоятельствах.» ← решения «Отдать часть работы Алексею» и «Посидеть у воды» (`protect_own_side`).
- Отклик, `varied`: «Сегодня твои решения были разными — общего рисунка за этот день пока не видно.»
- Не сложилось: «Способ действовать пока не сложился в одну линию — это тоже результат.»
- Пример `worldChange` с источником: «Лишние монеты остались у тебя: Тимон уже отвернулся и не заметил.» ← `{kind:'choice', day:4, slot:0, cardId:'c1_extra_change', choiceId:'keep'}` (факт `timon.trust = guarded`).
- Пример `unfinished`, `firm`, «завтра»: «Завтра Алексей придёт с вопросом о своей чашке.» ← `{kind:'scheduled', cardId:'c1_alexey_after_jug', day:2, latestDay:2}`.
- Пример `unfinished`, `firm`, без даты: «Странник вернётся к мастерской в ближайшие дни.» ← `c1_wanderer_returns`.
- Пример `unfinished`, `soft`: «О том, как ты бережёшь руку, Алексей ещё скажет своё.» ← факт `body.pace`, продолжение не `required`.
- Запрещено: «Ты обычно сначала анализируешь ситуацию.» на любом статусе, кроме `stable`.
