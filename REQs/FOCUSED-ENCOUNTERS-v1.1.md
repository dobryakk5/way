## 0. Резюме решения

Вместо произвольной новой встречи кубик выбирает непредвиденное **обстоятельство в контексте текущей истории героя**. Случайным остаётся результат броска, но не сюжетная допустимость события. Цель и намерение героя направляют *обычные свободные сюжетные сцены*, не подавляя последствия прежних поступков, обязательные сцены, самостоятельность других персонажей и диагностическую независимость.

В рамках v1.1:

1. **Не вводить третий реестр сюжетных линий.** Использовать `StoryLine` (`pace`, `apprentice`, `commitments`), действующий `threads.json` (14 записей), `GoalId`, `facts`, `scheduled` и `Condition`.
2. **Не вводить систему местоположений** и `anchorIds`; пространственная связность обеспечивается авторским текстом и существующими `requires`.
3. **Не менять persisted-схему `diceHistory`**: в ней уже фиксируются шесть кандидатов, `candidateOrigins`, грань и результат. Уровни релевантности выводить в диагностику/отчёт, не сохранять в игре.
4. **Не изменять нейтральные, probe и development-карточки.** Применять контекст только к обычным свободным story/routine. Режим `focusedEncounters` по умолчанию выключен.
5. **Сохранить один бросок за игровой день**, как в текущей проверке `journey.ts`.
6. **Одинаковый фильтр** использовать и для подготовки шести граней в `prepareEncounter`, и при прямом розыгрыше из `drawCard`, если кубик не используется.

## 1. Цель и игровые инварианты

Игрок видит непрерывную историю: цель → обстоятельство → решение → реакция мира → последствия. Игрок может сменить цель, но уже данные обещания и созданные последствия не исчезают.

Неизменны:

- 8 Action Logic, scoring/rubric, `heroDevelopmentProfile`, правила `neutral`, `probe` и диагностических evidence;
- развитие, в том числе дуга Эксперт → Достигатель, progression/reconciliation и условия переходов;
- `Card.at`, `routeSlot`, кризисы, `mustShowBy`, `scheduled` и `chain`, `once`/`cooldownDays`;
- фиксированные `sceneId`, `choiceId`, пары scene/choice, server outbox/event log, версии предъявленного контента;
- четыре грани жизни, свобода выбора действий, отдельная смена цели на 11-м и 21-м днях;
- фактические реакции, отложенные события, сохранённые текст, варианты ответов и изображения.

**Запрет:** никакого вычисления релевантности на основе `heroDevelopmentProfile`, `development`, `diagnostic*`, предполагаемой «зрелости» игрока или желательного психологического результата.

## 2. Терминология и источники истины

| Термин | Источник истины | Смысл |
| --- | --- | --- |
| Цель | `state.goal.id: GoalId` | `order`, `workshop`, `alexey` |
| Намерение | `state.declaredIntention: LifeFacet` | `work`, `relationships`, `body`, `inner` |
| Сюжетная линия | существующий `StoryLine` и `state.evidence[].line` | `pace`, `apprentice`, `commitments`; это журнал шагов **сюжетных линий**, не диагностический evidence |
| Открытое обязательство/история | существующий `threads.json` + `facts`, `opportunityState`, `scheduled` | Факт незавершённого сюжета, а не новая шкала |
| Обстоятельство | `Card` типа `situation`/`routine` | Условно допустимое событие из авторского набора |
| Сюжетная релевантность | **вычисляемая** характеристика карточки и состояния | Уровень P1–P5; не сохраняется |
| Диагностическое происхождение | `candidateOrigins` / `selectionOrigin` | Оставить прежнюю семантику `neutral`, `probe`, `adaptive` |

Не создавать новую persisted-сущность `activeThread`, отдельный «движок персонажей» или третий реестр линий. Для самостоятельных действий Тимона, Алексея, Марты и других использовать авторские сцены с `requires`, `effects.setFacts`, `effects.schedule`, `chain` и условиями времени.

## 3. Структура контента

### 3.1. Добавка к `Card`

Добавить **необязательный** блок авторских метаданных `story`:

```ts
interface FocusedStoryMeta {
  /** Существующий StoryLine, а не новый реестр. */
  lines?: StoryLine[];
  /** Ссылки на id уже существующего threads.json. */
  threadIds?: string[];
  /** Существующие GoalId. */
  goalIds?: GoalId[];
  /** Литературная роль; не влияет на диагностический scoring. */
  role: 'complication' | 'opportunity' | 'consequence' | 'relationship' | 'ambient';
  /** Только для специально вычитанной общебытовой сцены P5. */
  worldFallback?: boolean;
}

interface Card {
  // ... действующие поля
  story?: FocusedStoryMeta;
}
```

`role` описывает роль обстоятельства, **не** дублирует `Card.type='routine'`. Поле `lines` ссылается только на `pace | apprentice | commitments`; не добавлять фиктивную сюжетную линию `workshop` (это `GoalId`). `threadIds` означает реальный `id` существующего `threads.json`, а не название нового справочника.

У обычной свободной карточки, участвующей в focused-режиме, должен быть хотя бы один подтверждаемый якорь: непустые `lines`, `threadIds`, `goalIds` либо специально утверждённый `worldFallback:true`. Для `worldFallback` обязательны `role:'ambient'` и литературная проверка. Сами `facets` не считаются подтверждением сюжетной причинности.

Пример существующей бытовой сцены (показаны только добавляемые поля):

```json
{
  "id": "r_kiln",
  "story": {
    "lines": ["apprentice"],
    "goalIds": ["alexey", "workshop"],
    "role": "opportunity"
  }
}
```

Не создавать новые `choiceId` и не менять существующие ответы только ради разметки. Условия реальной доступности описывает прежнее `requires`; `story` не переопределяет `requires` и не меняет `effects`.

### 3.2. Нового реестра в `episodes.json` нет

Не добавлять в `episodes.json` `threadsRegistry`, `anchorIds` или статусные дубликаты `threads.json`. При необходимости расширить только правила авторинга/валидации существующих идентификаторов. Цели и дни пересмотра уже находятся в `episode.goals`, `goalReviewDays`, поэтому цель → линия определяется по метаданным конкретных карточек, а не по новой таблице переходов.

### 3.3. Открытость существующих `threads`

Реализовать чистую `isOpenStoryThread(thread, state, content)`, где:

- `kind:'fact'`: `thread.stages[state.facts[thread.fact]] === 'open'`;
- `kind:'opportunity'`: связанная возможность имеет `opportunityState[id] === 'open'` **и** была предъявлена игроку (`opportunityExposure[id]`);
- `kind:'chain'`: `state.scheduled` содержит ожидаемый `followUp.cardId` с ещё допустимым сроком; сам факт наличия текста в `threads.json` не означает открытости.

Точные поля брать из существующего типа `ThreadDefinition`. Не придумывать новые состояния; отсутствующие и нераспознанные значения считать «не подтверждено», а не «открыто». Условие `requires` всё равно должно выполняться.

## 4. Производный контекст

Создать `src/engine/storyContext.ts`:

```ts
interface StoryContext {
  goalId?: GoalId;
  intention?: LifeFacet;
  recentLines: StoryLine[];
  openThreadIds: string[];
  day: number;
  chapter: number;
}

function deriveStoryContext(
  state: GameState,
  content: GameContent
): StoryContext;
```

`recentLines`: уникальные значения `line` из **последних 8 записей** `state.evidence` (источник `Choice.lineStep`). Это не признак завершённости линии и не журнал диагностики. `openThreadIds`: определения из раздела 3.3.

Доступные зависимости функции: `state.goal`, `state.declaredIntention`, `state.evidence` (только сюжетное), `state.facts`, `state.opportunityState`, `state.opportunityExposure`, `state.scheduled`, `day`, `chapter`, определения `threads.json`. Она **не должна читать** поля `state.heroDevelopmentProfile`, `state.development`, `Card.diagnostic`, диагностические векторы, confidence и источники выбора логики. Запрет подтвердить тестом dependency/isolation.

Контекст вычислять **до подготовки новых кандидатов**; после сохранения `diceHistory` не пересчитывать кандидатов по контексту.

## 5. Формальная релевантность P1–P5

Для карточки `c` и контекста `x` определить:

- `G`: `c.story.goalIds?.includes(x.goalId)`;
- `L`: пересечение `c.story.lines` с `x.recentLines` непусто;
- `T`: пересечение `c.story.threadIds` с `x.openThreadIds` непусто;
- `I`: `c.facets?.includes(x.intention)`;
- `W`: `c.story.worldFallback === true && c.story.role === 'ambient'`.

**Требование:** все эти признаки вычисляются только из перечисленных полей, а кандидат до оценки проходит базовую `eligible` и ограничения `freePool`.

| Уровень | Формула | Значение |
| --- | --- | --- |
| P1 | `G && (L || T)` | Цель и продолжение начатой линии/обязательства |
| P2 | `L || T` | Прямая связь с незавершённым сюжетом |
| P3 | `G` | Прямое развитие выбранной цели |
| P4 | `I` и карточка размечена `story` | Связь с намерением в естественном контексте |
| P5 | `W` | Специально разрешённое нейтральное бытовое обстоятельство |
| Исключить | иначе | Нет подтверждаемой сюжетной связи |

Первое совпавшее условие определяет tier. Приоритет — не оценка качества выбора и не вероятность успеха. Факт, что `requires` выполнен, не является самостоятельным доказательством P3; он только ограничивает доступность.

Для анализа хранить вычисленные `tier` и основание `G/L/T/I/W` **в отладочном trace и отчётах**, но не в `diceHistory` и не в серверном событии выбора.

## 6. Сборка шести граней

**Точка реализации:** `src/engine/journey.ts:prepareEncounter` с использованием общей чистой функции из `focusedEncounters.ts`. Исходный порядок приоритетов `drawCard` не менять. Важное действующее условие: если в `diceHistory` уже есть запись за день, второго броска **нет**.

### 6.1. Защищённый состав

1. Вызвать прежний `freePool` и прежние условия `adaptiveSelectionOn` / `independentPool`; отобрать прежний детерминированный shuffle по `deterministicRandom(seed, day, slot, 'candidate:'+card.id, episodeId)`, при точной ничьей — `id`.
2. Определить прежнюю доступность `probe` по `probeScenes`, **не более одного** кандидата probe.
3. На базовом срезе `5` (если есть probe) либо `6` зафиксировать все **необычные сюжетные** позиции, которые существующий `isFacetWeightedDrawCandidate(card)` не разрешает перевзвешивать. Это включает нейтральные диагностические и прочие защищённые категории.
4. `facetAdjustedSlice` может продолжать определять обычные story-позиции, но в focused-режиме они **заменяются** на контекстные; не применять после этого второе независимое перевзвешивание по сферам.
5. Не менять состав и происхождение защищённых neutral-кандидатов при одинаковом состоянии и seed. Сохранить `FACET-2` между разными распределениями внимания и при сравнении focused ON/OFF, если набор защищённых кандидатов в legacy одинаков.
6. Не менять селектор самого probe и ограничения последовательности independent/adaptive. Карточки `development` не размечать и не включать в focused-story.

Оставшиеся позиции (`storySlots = 6 - protectedCount - probeCount`) заполнять по §6.2. Запрещено перераспределять защищённые позиции в пользу цели.

### 6.2. Правило наполнения story-позиций

- Основные позиции выбирать сверху вниз: P1 → P2 → P3 → P4 → P5, **без возвращения** карточек.
- Внутри одного tier использовать детерминированную взвешенную выборку. Базовый вес карточки и действующий `facetAttention` учитывать **один раз**; эффект `declaredIntentionPrior` не дублировать.
- Если `storySlots >= 2`, существует альтернативная подходящая карточка и она отличается от основного контекста, **одну** позицию оставить для сюжетного разнообразия: предпочтительно `T/L` другой открытой линии, иначе карточку намерения `I` другой сферы. Сначала обеспечить эту позицию, остальные — по P1…P5.
- Если альтернативы нет, не создавать искусственное разнообразие: заполнить позиции по обычному приоритету.
- Нельзя вставлять одну карточку дважды. Нельзя добавлять нерелевантные legacy-story события ради достижения шести.
- Итоговый список кандидатов перемешать детерминированно тем же семейством RNG, чтобы уровень P1 не означал закреплённую грань 1. Только **после фиксации** списка делать честный бросок.

Сохранить существующую равновероятность граней; P1–P5 определяют **состав набора**, но не вероятность отдельной грани.

### 6.3. Дефицит кандидатов

Если после заполнения защищённых и контекстных позиций получилось меньше шести **различных** допустимых кандидатов, `prepareEncounter` не создаёт неполный `diceHistory`. В этом слоте выполнить **прямой отбор** через общую функцию §7. Не дублировать варианты для кубика.

Если подходящих карточек вовсе нет, это `FOCUS_POOL_EMPTY` — ошибка данных, подлежащая обнаружению при тестировании/симуляции. Не возвращаться молча в общий случайный story-пул внутри активированного интервала.

## 7. Фолбэк при прямом отборе: обязательная вторая точка

**Точка:** `src/engine/draw.ts`, последний путь `drawFreePoolWeighted(state, content, pool)`.

Необходимо предусмотреть единую функцию отбора для обоих режимов:

```ts
selectFocusedStoryCandidates(state, content, freePool): {
  cards: Card[];
  tiers: Record<string, 1|2|3|4|5>;
}
```

В новом прямом отборе:

1. Сначала сохранить существующие проверки fixed/route/obligations/crisis/deadline/scheduled/development/probe в `drawCard`.
2. Для обычного свободного `pool` вычислить ровно такой же контекстный список, что для кубика.
3. Сохранить независимый исходный выбор типа *protected vs story* по существующей логике прямого розыгрыша там, где он применим. Если исходно выбран защищённый кандидат — вернуть его без замены.
4. Если исходно выбрана story-карточка — перевыбрать **только среди релевантных story-кандидатов**, с тем же tier-приоритетом и `facetAttention` без двойного веса.
5. Если story-кандидатов нет, не показывать произвольную историю. Вернуть допустимый защищённый кандидат через детерминированную ветку, если он есть; иначе ошибка `FOCUS_POOL_EMPTY`. Ситуацию отдельно учитывать в QA-отчёте, поскольку она способна менять долю диагностики.
6. Для прямой ветки использовать только `deterministicRandom(seed, day, slot, salt, episodeId)`, без `Math.random`. При неизменном состоянии результат повторяем.

Подходящие события в активированном периоде всегда проходят §5, независимо от того, удалось ли показать кубик.

## 8. Защита диагностики и development

**Отбор не вправе:**

- читать профиль героя и определённую/предполагаемую логику;
- менять `neutral`, `probe` или `development` карточки ради фокуса;
- менять диагностические векторы, `selectionOrigin`, scoring/rubric, confidence;
- искусственно уменьшать независимое наблюдение ради цели;
- создавать несколько probe на один бросок;
- заменять уже открытый или сохранённый выбор.

Обязательные регрессии:

- **FACET-1:** при одинаковых предъявленных решениях подсчёт scoring/profile идентичен;
- **FACET-2:** нейтральные кандидаты одинаковы при различном внимании; контекстный отбор не заменяет защищённые neutral;
- независимость `probeScenes` и отдельного селектора development;
- ни одна из функций `deriveStoryContext`, `rankFocusedStory`, `selectFocusedStoryCandidates` не читает диагностический/развивающий профиль.

Литературная адаптация neutral/probe-сцен **не входит в v1.1**, даже если они временно выглядят самостоятельными эпизодами. Это отдельный контентный проект с повторной калибровкой.

## 9. Rollout и покрытие контента

Добавить в `src/content/data/development-profile.json` и соответствующие строгие схемы:

```json
{
  "rollout": {
    "focusedEncounters": false
  },
  "focusedEncounters": {
    "fromDay": 1,
    "throughDay": 10
  }
}
```

Фрагмент показывает **новые поля** в существующем объекте: остальные rollout-переключатели и конфигурация должны быть сохранены.

Включение focused для данного слота:

`rollout.focusedEncounters && fromDay <= state.day && state.day <= throughDay`.

- При выключенном флаге либо за пределами диапазона сохранять **побитно прежний алгоритм** без изменений порядка RNG.
- В пределах диапазона неразмеченные **обычные** story-карточки исключать из контекстного отбора, а не помещать автоматически в P5.
- Neutral/probe/development/route/обязательные карточки не исключать из своих старых подсистем из-за отсутствия `story`.
- Этап 1: покрыть и включить `1–10` (после content lint и симуляций).
- Этап 2: доразметить и переработать дни `11–30`, затем расширить диапазон до `1–30`.
- Запрещается выставлять `throughDay:30`, пока симулятор не подтвердил покрытие каждого достижимого контекста.

| «Кого принесёт этот день?» | «Как повернутся обстоятельства?» |
| «Выпало N · встреча начинается» | «Выпало N · история продолжается» |

Длительность анимации и автопереход сохраняются. Не показывать игроку P1–P5, источники диагностики, вес и «правильную» грань.

При прямом отборе без кубика переход не должен выглядеть телепортацией: предъявляемая карточка должна быть самостоятельно понятна из её авторского текста. Если требуется соединительная фраза, хранить её в самой карточке/условном `textVariant`, не создавать необъяснимую UI-заглушку.

## 11. Правила контента и проверяемые определения

- **Контекстно обоснованная карточка:** `eligible==true`, присутствует `story`, получен tier P1…P5 с машинно проверяемым основанием.
- **Связь с историей:** P1/P2/P3; **связь с намерением:** P4; **редакторски разрешённый бытовой контекст:** P5.
- **Неразрешённая произвольная вставка:** показ обычной story-карточки без tier в активированном периоде; допустимое значение — 0.
- **Значимое последствие:** изменённый факт или флаг, назначенное продолжение либо наблюдаемая реакция, реально читаемая дальнейшим `requires`, `textVariant`, `trace`, `ending`/`summary` или `scheduled`. Для каждого добавленного writer-поля должен существовать читатель; существующая инфраструктура WORLD-IMPACT применяется к существенным выборам.
- **Пустой слот:** одна из `30 × 4 = 120` позиций `(day, slot)`, для которой после всех обязательных/специальных/контекстных селекторов нет допустимой карточки. В слоте без кубика одна полноценная карточка всё равно обязательна.
- **Сюжетное разнообразие:** минимум один альтернативный story-кандидат на 6 гранях при условии `storySlots>=2` и наличия подходящей альтернативной активной линии или сферы. Не является требованиями к каждому прогону, если альтернативы недоступны.

Авторская вычитка: карточка должна естественно отвечать на «почему сейчас?», «чем связана?», «что выбирает герой?», «где увидим последствие?». Формальная метка сама по себе литературного качества не гарантирует.

### 11.1. Пример линии Алексея

Текущая цель `alexey`, свежая линия `apprentice`. Подходящие контекстные обстоятельства: изделие треснуло, Алексей изменил форму, Тимон заинтересовался его работой, ученик просит самостоятельно назвать цену. Реальное авторское событие выбирается из заранее написанных карточек при выполнении `requires`; игровой движок не сочиняет произвольный текст.

Смена цели на `workshop` в день 11 не отменяет обещаний Алексею и ожидаемые `chain`. На 21-й день тот же контракт действует для новой цели.

## 12. Валидация и тесты

### 12.1. Статический lint (`scripts/schema.ts`, `scripts/check-content.ts`)

Проверять:

1. `story.lines` — только `StoryLine`; `story.goalIds` — только `GoalId`; `story.threadIds` реально существуют в `threads.json`.
2. При наличии `worldFallback:true` обязательно `role:'ambient'`, запрещены конфликтующие автоматические «якоря места».
3. Новые карточки текущего rollout-диапазона имеют обязательные обоснования и доступные условия; проверка покрывает реальные состояния, не только непустые поля.
4. Уникальность `id`/`choiceId`, `once`/`cooldownDays`, достижимость `scheduled` и дедлайнов.
5. Для добавленных эффектов существуют подтверждаемые читатели; не создавать мёртвых flags/facts.
6. Защищённые диагностические карточки и their scoring не изменились по сравнению с baseline; новым `story` их не размечать.
7. Истории вне coverage не объявлены активными случайно.

### 12.2. Юнит-тесты

Добавить `storyContext.test.ts`, `focusedEncounters.test.ts`, расширить `journey`, `draw`, `save` и facet-тесты:

- P1–P5 и исключение без основания;
- `isOpenStoryThread` для `fact`, `opportunity`, `chain`;
- приоритет намерения и другой активной линии;
- 0 или 1 probe, уникальные шесть кандидатов, сохраняемые neutral;
- независимость от development/profile и `FACET-2`;
- равномерность граней `fairDieFace`, детерминированное формирование кандидатов и прямой fallback;
- отсутствие повторного броска в тот же игровой день;
- стабильность текущего `cardId`, `choiceIds`, `candidateOrigins`, `face` после reload;
- без `focusedEncounters` старые результаты совпадают с baseline.

### 12.3. Интеграционные сценарии

A. Цель `alexey` в днях 1–10; контекстные story-события соответствуют подтверждённым обстоятельствам.

B. На **11-м дне** герой меняет цель на `workshop`; фокус перераспределяется, уже запланированные продолжения Алексея остаются.

C. На **21-м дне** цель меняется снова; сохранить все обязательства и дедлайны.

D. Работа занимает внимание; обязательная сцена отношений и кризис не вытесняются.

E. Появляется probe; его защищённая позиция и `selectionOrigin` сохранены.

F. Меньше шести кандидатов: кубик не показывается, прямой `drawCard` **не обходит** контекстный фильтр.

G. Перезагрузка после подготовки кандидатов, после граней и после выбора не меняет сохранённую историю.

H. В днях 11–30 до расширения coverage алгоритм точно legacy; после расширения — контекстный.

I. Недостаток контекстных карточек приводит к регистрируемой ошибке покрытия, а не незаметному выбору из общего пула.

### 12.4. Симуляция

Перед реализацией сохранить baseline команд `npm run check`, `npm run build`, `npm run simulate`, `npm run simulate:profile`, `npm run facets:simulate` (с существующими параметрами); запускать новые сравнения с теми же seeds и политиками.

Для **каждой** существующей политики провести по **1000 завершённых 30-дневных прогонов**, включая проверку всех `4 × 30` слотов. Отдельно просимуляровать состав шести граней на уровне кандидатов, а не только выпавшее событие.

Сравнить в отчёте:

- 0 пропусков обязательных событий и дедлайнов, 0 `FOCUS_POOL_EMPTY` и пустых слотов;
- 0 необоснованных обычных story-карточек в активном диапазоне;
- число защищённых neutral/probe, сохранение FACET-2, диагностические `N/W/K`, coverage, confidence, доли стадий относительно baseline;
- число бросков, долю прямых отборов, уникальность граней;
- разнообразие сфер/линий и фактические возвращения последствий;
- количество неисполненных scheduled, сбои сохранений и устойчивость after-reload.

Точные пороги непонижения качества диагностики принимать по зафиксированным baseline и действующим рубрикам. Нельзя подбирать новые пороги после просмотра результатов. Любая статистически/практически заметная деградация диагностики блокирует rollout до анализа.

## 13. Сохранения, contentVersion и PWA

**Persisted `GameState` и `diceHistory` v1.1 не расширять.** В `src/persistence/save.ts` сохранён строгий `dice5` с массивами длиной 6; если в ходе разработки всё же понадобится сохранять новые свойства, требуется **новое отдельное решение, версия persisted-схемы, валидатор и явная миграция**.

Менять требуется `scripts/schema.ts` для новых *контентных* метаданных `Card.story`, конфига `focusedEncounters` и строгого `rollout`; и `types.ts`. Это не равно миграции игровых сейвов.

Однако обновление **текстов/choices/визуалов** может потребовать обновления `CONTENT_VERSION` и механизмов совместимости. В текущем коде `migrateSave` принимает ограниченный набор совместимых контентных версий: новая версия с изменённой семантикой предъявленных карточек не должна автоматически признаваться совместимой.

Релизная проверка должна включать старую вкладку/PWA из кэша, новую вкладку, открытый кубик, сохранённый выбор, серверную синхронизацию и сохранение прежних авторских ID. **Нельзя обещать, что старый PWA-клиент прочитает сохранение нового contentVersion** без специально реализованной стратегии совместимости. Новые версии контента выпускать по установленной процедуре обновления/миграций, не перезаписывая зафиксированный старый выбор.

## 14. План работ и критерии готовности

### Этап 0 — baseline (без фиктивного «ремонта экспорта»)

- Зафиксировать SHA `main`, versions, число карточек и реальные селекторы.
- Запустить сборку/тесты/симуляции; записать ошибки, если есть.
- Создать таблицу кандидатов и baseline по диагностике/слотам.

### Этап 1 — движок под выключенным флагом

- Схемы `Card.story` и `focusedEncounters`.
- `deriveStoryContext`, оценка P1–P5, сохранение protected-кандидатов.
- Интеграция в **двух точках**: `journey.ts:prepareEncounter` и `draw.ts:drawCard`/direct fallback.
- Отладочный trace без новых persisted-полей.
- Тесты ON/OFF, FACET-2, одна кость в день, idempotency.

### Этап 2 — контент и rollout дней 1–10

- Разметить реальные обычные сцены первых двух глав (не neutral/probe/development/route-only).
- Дописать связи/последствия там, где недостаточно сюжетного основания.
- Провести симуляции и редакторскую проверку, включить `fromDay:1, throughDay:10`.

### Этап 3 — продолжение 11–30

- Переработать карточки глав 3–4 с учётом существующих `StoryLine`, `threads`, фактов и смены цели 11/21.
- Проверить все переходы между главами, расширить coverage до 30.

### Этап 4 — релиз

- Пройти полный regression/test suite, сохранения, PWA, контентный lint, сравнение baseline, ручной плейтест.
- Разрешить включение флага по результатам проверки; merge в `main` только после review.

**Критерии приёмки:**

| № | Требование | Проверка |
| --- | --- | --- |
| AC-1 | OFF = без изменений legacy-селектора | Regression равен baseline |
| AC-2 | ON не допускает обычную story-карточку без P1–P5 в активном периоде | 0 нарушений в тестах и симуляциях |
| AC-3 | 0 пропущенных `at`, `chain`, `mustShowBy`, `route` и незакрытых дедлайнов | 1000 прогонов каждой политики |
| AC-4 | 0 пустых позиций из 120 в каждом прогоне; 0 `FOCUS_POOL_EMPTY` | Симуляции |
| AC-5 | FACET-2 и ограничения neutral/probe/development сохранены | Unit + baseline |
| AC-6 | Шесть уникальных кандидатов, не больше одного probe, честный кубик, максимум один бросок/день | Unit/интеграционные |
| AC-7 | Fallback в `drawCard` фильтрует story ровно как `journey.ts` | Unit/интеграционные |
| AC-8 | Старая история не пересчитывается после reload или изменения rollout | Persistence + PWA-тесты |
| AC-9 | Все новые факты/флаги имеют реальные читатели; последствия наблюдаемы | Lint + ручная вычитка |
| AC-10 | `npm run check`, `npm run build` и согласованные симуляции проходят | CI + reports |

## 16. За пределами v1.1

Нет генерации сюжета ИИ, свободной карты/перемещения, новой экономики, третьего реестра линий, психологического scoring по цели, изменения нейтральных диагностических сцен, смены существующих stages, переписывания серверной модели persistence и новых persisted-полей кубика.

### Финальное правило

**Кубик меняет обстоятельства, а не намерение героя. Выбор героя меняет мир. Мир возвращает последствия.**
