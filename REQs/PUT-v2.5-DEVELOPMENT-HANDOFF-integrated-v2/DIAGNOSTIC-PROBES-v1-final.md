# DIAGNOSTIC-PROBES-v1
## «Путь»: 21 profile-conditioned диагностическая probe-сцена для семи соседних пар

**Статус:** authoring draft v1 для blind-калибровки; не включать в adaptive selector до проверки  
**Дата:** 5 октября 2026  
**Основание:** `DEVELOPMENT-RUBRIC-v1-final.md`, `DEVELOPMENT-BEHAVIOR-MATRIX-v1.md`, `IMPLEMENTATION-v2.4-HERO-PROFILE-v2-reviewed.md`

## 1. Назначение

Ровно 21 сцена: по 3 на каждую соседнюю пару. Все они проектируются как `selectionOrigin = "probe"` и не являются development-arc контентом.

Каждая сцена имеет третий правдоподобный вариант, лидирующий **вне целевой пары**. Это защита от самоподтверждения: сам факт показа probe не должен автоматически поднимать две проверяемые логики при любом ответе.

`probe` является **profile-conditioned diagnostic sampling**: selector выбирает его по двум ведущим логикам `currentDistribution`. Поэтому probe не является статистически независимым от профиля. При этом `neutral + probe` являются **profile-eligible diagnostic evidence**, потому что не выбираются по `developmentCurrent`, `activeArcId`, `transitionTarget` или development/adaptive hypothesis.

## 2. Формат `LogicVector`

В документе используется порядок:

`[O,D,E,A,I,S,Al,Ir] = [opportunist,diplomat,expert,achiever,individualist,strategist,alchemist,ironic]`.

При переносе в JSON массив разворачивается в объект с ровно 8 ключами.

Во всех вариантах v1: сумма `1.00`, две ненулевые компоненты, максимум `0.65`.

## 3. Общие правила

- Probe показывается только в свободном диагностическом слоте.
- `distinguishes` = целевая соседняя пара.
- Ведущие логики для выбора probe берутся из `currentDistribution`.
- Сцена не имеет stage/development gating.
- Карточка не является частью active development arc.
- Уже показанная сцена не меняет текст, варианты или origin после reload/пересчёта.
- Каждая сцена используется максимум один раз за прохождение.
- До production весь пул проходит blind-review.

# 12. Position balance v1

Для каждой соседней пары её три сцены используют ротацию ролей:

```text
scene .01: A=left,  B=right, C=control
scene .02: A=right, B=control,C=left
scene .03: A=control,B=left,  C=right
```

Следовательно, внутри каждой пары ни одна позиция A/B/C не является постоянным «более ранним», «более поздним» или контрольным ответом. При blind-review порядок дополнительно перемешивается независимо от authoring-порядка.

# 13. Blind-review

Для каждой сцены второй редактор, не видя исходных векторов, отмечает:

1. лидирующую логику каждого choice;
2. вторую логику;
3. какую соседнюю пару фактически различает сцена;
4. требует ли разметка угадывания мотива;
5. выглядит ли какой-то вариант «правильнее» по языку;
6. реалистичность trade-off по шкале 1–5.

Правило решения:

- спор только о второй логике → можно смягчить веса;
- спор о лидере → переписать вариант;
- спор о самой различаемой паре → исключить сцену из probe-пула;
- моральная подсказка → переписать формулировки всех вариантов.

# 14. Критерий production

Пул не включается в targeted probe selector, пока:

- [ ] 21/21 сцен проходят content validator;
- [ ] после отбраковки остаётся минимум 3 принятых сцены на каждую пару;
- [ ] Cohen’s κ по лидирующей логике ≥ 0.70;
- [ ] mixed/insufficient simulation не создаёт ложный stable;
- [ ] нет системного перевеса поздних логик из-за языка вариантов;
- [ ] лимит доли probe в независимом окне реализован;
- [ ] calibration report сохранён.

# 15. Следующий шаг

После blind-review использовать результаты для:

1. корректировки `DEVELOPMENT-RUBRIC-v1`, если ошибка системная;
2. создания `NEUTRAL-DIAGNOSTIC-CONTENT-v1`;
3. проверки production-вариантов development arcs;
4. первой полной `simulate-profile` калибровки.
