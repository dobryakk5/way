## 0. Как выбор влияет на центры

Вводная для всех, кто правит влияние выбора. Это пересказ, а не норма: при расхождении прав этот раздел по документам из ссылок.

**Что такое центр.** Восемь логик действия от Оппортуниста до Ироника — это то, *как* герой организует смысл и действие. Это не оценка доброты, ума или зрелости (rubric §13.1, `RECONCILIATION-v2.md` §11). Подробная карта центров (картина мира, сила, слепое пятно, ограничение, переход к следующему) — `DEVELOPMENT-MODEL-v1.md` §2–17. Киган, Кук-Гройтер, Спиральная динамика, Маслоу и Кольберг — линзы для автора, а не отдельные шкалы: таблица соответствий и запрет на автоматический перевод — в конце `DEVELOPMENT-BEHAVIOR-MATRIX-v1.md`.

**Путь от ответа до профиля.**

```
вариант ответа
  diagnosticAction.vector          8 чисел, сумма 1, максимум 0,70, ≥ 2 ненулевых   rubric §7
  rationale                        основание по шести осям SELF … UNCERTAINTY       rubric §3–4
  card.diagnostic.developmentWeight  вес свидетельства сцены, 0,70–0,90 (не «уровень»)  rubric §8
        │
        ▼  вклад кейса — алгоритм 2, «контраст»
  выбранный вектор − среднее векторов отвергнутых вариантов этой карточки;
  отрицательное обнуляется, остаток нормируется до 1
        │
        ▼  источники кейса                                                              ADDENDUM §5
  действие 0,50 · мотив 0,30 · последующее поведение 0,20, всё × developmentWeight
        │
        ▼  currentDistribution — доли логик по последним 24 кейсам neutral/probe
        │
        ▼  observedPrimary (тот же кандидат два вечера подряд), confidence,           ADDENDUM §6–7
           leadingEdge, fallback, emergingSignals
        │
        ▼  developmentCurrent меняется только через дугу развития, а не через профиль  DEVELOPMENT-MODEL §21
```

ADDENDUM — `REQs/REQUIREMENTS-v2.4-ADDENDUM.md`. Контраст (ветка `2`) и её пороги описаны в поправке в конце его §5. Ветка `1` засчитывает весь вектор выбранного варианта. Новые игры идут по `currentAlgorithmVersion` из `src/content/data/development-profile.json`.

**Какой документ главнее.** Отдельные документы пакета лежат в `REQs/PUT-v2.5-DEVELOPMENT-HANDOFF-integrated-v2/`.

| Вопрос | Решает | Уступает ему |
|---|---|---|
| Что значит центр, переход, дуга | `DEVELOPMENT-MODEL-v1.md` | всё ниже |
| Какой вектор у ответа, границы пар, шесть осей | rubric (`DEVELOPMENT-RUBRIC-v1-final.md`) | карточки пакета, скин |
| Как свидетельства превращаются в центр | ADDENDUM (вместе с поправкой ветки `2`) и `algorithms` в `development-profile.json` | `REQUIREMENTS-v2.4.md`, в котором ADDENDUM переопределяет противоречащее |
| Сферы и частота сюжетных сцен | `FACET-ATTENTION-v1.md` | — |
| Как писать тексты карточек | этот стандарт | — |
| Конкретная карточка | структура `content-src/v2.5/*.json` | скин и собранный `src/content/data` |

Если смысл карточки противоречит модели или rubric, исправляют карточку. Если алгоритм противоречит смыслу модели, это выносят на отдельное решение и не правят самостоятельно ни алгоритм, ни модель. Пересказы (этот §0, отчёты, комментарии в коде) нормой не являются.

**Что из этого следует при правке.**
- **Вклад зависит от соседей.** При контрасте засчитывается то, чем выбор *отличается* от отвергнутых вариантов. Правка вектора одного варианта меняет вклад всех вариантов карточки, поэтому карточку смотрят целиком.
- **Сфера не влияет.** `card.facets` и `servesFacets` в расчёт не входят (§1–2, `FACET-ATTENTION-v1.md`).
- **Ресурсы и качества не влияют на профиль**, но могут подсказать «правильный» ответ и так исказить выбор (§10).
- **В профиль попадают только карточки с `diagnosticAction`, мотивом или продолжением.** Сюжетные сцены не размечаются. Карточки дуг двигают развитие через `developmentEvents` — это отдельный механизм.

**Где править и как проверить.**
- Вектор, rationale, вес и роли — в структуре `content-src/v2.5/*.json`, не в скине и не в собранном `src/content/data` (§12). Затем `npm run v25:build` и `npm run check`.
- Каждая ненулевая компонента должна иметь основание в rationale. Автоматической нормализации нет: превышение 0,70 исправляют руками.
- Коэффициенты источников, окно и пороги — `algorithms` в `development-profile.json`. Ветки неизменяемы: изменение — это новая ветка с новым номером (ADDENDUM §12 «Версионирование методики»).
- Правка вектора — это новая версия разметки, а не тихая правка. Журнал свидетельств в сохранениях сверяется с векторами текущих карточек (`validateHeroDevelopmentProfile`).
- Эффект на распределение: `npm run v25:simulate` (`SIM_SCORING=contrast` для текущей ветки), `npm run simulate:profile`, `npm run profile:calibration`. Смысл проверяет слепая разметка редактора (rubric §13).

## 1. Главный принцип: две независимые оси

У каждого выбора две разные смысловые оси, и они не должны сцепляться.

| Ось | Где хранится | Вопрос | Что читает |
|---|---|---|---|
| **КАК** человек действует | `diagnosticAction` (вектор логик) или `developmentEvents` | какой способ действия виден в выборе | профиль героя, развитие |
| **КУДА** он вкладывает внимание | `choice.servesFacets` | в какую сферу жизни уходят время и силы | `facetAttention` (частота сюжетных сцен по сферам) |

И отдельно, на уровне карточки: `card.facets` — **о чём** жизненная ситуация. Значения `card.facets` и `servesFacets` не обязаны совпадать: ситуация началась вокруг работы и отношений, а игрок решил отдохнуть — вариант с `servesFacets: [body]` честный и хороший.

Сферы: `work` (дело и деньги), `relationships` (отношения), `body` (тело и здоровье), `inner` (внутренний мир).

## 2. Чего нельзя: склеивать сферу и логику

Запрещён шаблон «работа = Достигатель, отношения = Дипломат»:

```
A. Остаться работать        → Достигатель + work
B. Пойти к семье            → Дипломат + relationships
```

Если повторять, игра сама создаст корреляцию, и профиль начнёт читать сферу вместо способа действия. Нужно, чтобы в разных сценах один и тот же человек был Дипломатом в работе, Экспертом в отношениях, Достигателем в здоровье, Стратегом во внутренней жизни — и наоборот.

Не превращать карточки в «A — работа, B — отношения, C — здоровье, D — внутренний мир»: быстро станет заметно и будет похоже на тест. Естественно так: одна карточка — 2 сферы, другая — 3, третья — все варианты внутри одной сферы, но с разными способами действия. Баланс создаёт совокупность карточек.

## 3. Четыре вопроса автору (проверка каждой карточки)

1. `card.facets` честно описывает исходную жизненную ситуацию?
2. `servesFacets` описывает последствие выбора внимания, а не просто тему текста?
3. Есть ли между вариантами настоящий выбор, куда вложиться, **если ситуация это допускает**?
4. Не сделаны ли варианты искусственно разными только ради разных сфер?

## 4. Что менять, а что нет

| Тип | Правила для сфер |
|---|---|
| **Neutral** (партия 1) | не менять. Сфера — свойство ситуации; у всех вариантов `servesFacets = card.facets`. Neutral не зависит от `facetAttention`, его задача — определять центры. Сейчас: facet × логика сбалансированы ровно (по 4 лучших варианта каждой логики в каждой сфере). |
| **Probe** (партия 2) | не менять ради сфер. Сфера — декорация, задача пробы — различить соседние центры. Известное ограничение пакета: у проб факт сферы жёстко привязан к паре (например, в `body` нет проб Оппортунист/Алхимик/Ироничный, а в `relationships` — Эксперта). Вариантов `servesFacets ≠ card.facets` нет. |
| **Development** (дуги) | не писать ради сфер: они ведут по дуге центра. `servesFacets` — сфера карточки, если ситуация не говорит иного. |
| **Сюжетные сцены** | единственный тип, где `servesFacets` содержательно различает варианты. Проверять смыслом; текст переписывать не нужно. Сейчас из 254 вариантов сюжетных и сюжетно-развитийных карточек 13 выходят за `card.facets` — не править автоматически, только просмотреть. |

## 5. Как писать сцену (сам вопрос)

Сцена — это не вопрос «кто ты?», а жизненная развилка, в которой у каждого варианта есть своя цена.

1. **Сначала факт, потом психология.** Описать, что случилось и кто рядом, без оценки и без чувств героя за него. Плохо: «Ты растерян и не знаешь, как быть». Хорошо: «Тимон уже ждёт товар, а у шести ручек трещина».
2. **Настоящий компромисс.** В сцене должно быть то, что нельзя получить сразу всё: срок против качества, своя выгода против общего уговора, простая починка против разбора причин. Если «правильный» ответ очевиден, сцена не диагностирует.
3. **Каждый вариант честно выбираем.** Живой человек с любой из восьми логик должен найти в сцене свой вариант, который не звучит глупо или стыдно.
4. **Сцену не надо читать по-другому.** В тексте не должно быть слов, которые заранее подталкивают к одной логике: «все так делают» толкает к Дипломату, «по правилам» — к Эксперту, «цель важнее» — к Достигателю.
5. **Тема сцены не определяет логику** (rubric §11). Деньги ещё не Оппортунист, помощь ещё не Дипломат, расчёты и записи ещё не Эксперт, цифры успеха ещё не Достигатель, «быть собой» ещё не Индивидуалист, длинный план ещё не Стратег, чутьё ещё не Алхимик, шутка ещё не Ироничный. Логику определяет то, **из чего** принято решение, а не о чём оно.
6. **Пробы и neutral не зависят от стадии героя.** Никаких `heroStage`-вариантов текста, условий на `developmentCurrent` и событий развития в диагностических карточках (rubric §12).
7. **Объём:** 1–2 короткие фразы, до ~200 символов. Если без третьей фразы непонятно, где развилка, значит, развилка ещё не найдена.

## 6. Как писать варианты

### 6.1. Для всех типов

- **Варианты различаются способом действия, а не моралью, длиной или старанием.** «Поздняя» логика не написана привлекательнее, длиннее или красивее (rubric §12). Разница длины вариантов одной карточки — ориентир не больше ~15 символов; самым длинным не должен систематически оказываться один и тот же тип варианта. Это ориентир для новых карточек: в уже влитых neutral разброс больше у 14 из 32, в пробах — у 3 из 21; массово не правим.
- **У каждого варианта своя реальная цена**, и это видно в ресурсах (§10): нет варианта, лучшего по всем ресурсам сразу.
- **Действие, а не мотив.** Вариант описывает, что герой делает. Не приписывать мотив, который можно только угадать: «из страха», «чтобы понравиться». Мотив игрок выбирает отдельно, в вопросе о мотиве.
- **Различитель сохраняется целиком** (§7): если у вектора две ненулевые компоненты, в тексте должны быть слова, которые несут обе.
- **Позиция не подсказывает.** Порядок и роли вариантов берутся из пакета и уже сбалансированы (rubric §16); при переписывании текста их не переставлять.
- **Ранний вариант — изнутри, а не карикатура.** Варианты Оппортуниста, Дипломата, Эксперта и Достигателя легко написать сухо или с вызовом, и тогда поздние выглядят лучше просто на контрасте. Правила:
  - у варианта видна его собственная причина или выгода, взятая из текста пакета: «Очередь есть очередь: исключение всех подведёт» вместо лозунга «Очередь есть очередь. Порядок не ломаю»;
  - цена — фактом, а не вызовом: «даже если обидится», а не «пусть обидится»;
  - без ограничителей «только», «лишь», если ограничение не составляет сути варианта: «Дам ясную сумму, срок и условие — под конкретное дело» вместо «Дам только ясную сумму, срок и условие». В `probe.od.01` «Назову только Алексея» «только» оставлено: в нём весь смысл самозащиты;
  - без слов, которые сами по себе стыдят: «втихую», «отделаюсь». Было: «Использую втихую — выгода моя»; стало: «Обращу знание себе в выгоду, источник не выдам».
- **Не повторять формулировку в разных карточках.** Одна и та же фраза у одной логики («пусть не думают, что со мной можно так» стояла в двух карточках) — шаблон, по которому игрок и редактор узнают логику. Линтер ловит дословные повторы в neutral и пробах. В сюжете и старых повторных попытках дуги одинаковые метки — это версии одной сцены, их не трогаем.
- **Первое слово не принадлежит логике.** Если половина Индивидуалистов начинается со «Спрошу», а Ироничные — с «Не…», глагол становится подсказкой. Ориентир: одно первое слово — не больше четверти вариантов одной логики в пуле (таблица линтера).

### 6.2. Neutral (4 варианта)

- У каждого варианта своя ведущая логика; в одной сцене четыре разные ведущие логики.
- Баланс пула (по 4 лучших варианта каждой логики на каждой позиции A/B/C/D, по 8 сцен на сферу) задан структурой пакета. Тексты переписываются, структура — нет.
- `servesFacets = card.facets` у всех вариантов (§4).

### 6.3. Probe (3 варианта)

- Роли: **два варианта различают соседнюю пару** (`distinguishes`), **третий — контроль**, правдоподобный вариант с ведущей логикой вне пары. Контроль не должен быть «очевидно не тем»: если его никто не выберет, проба различает хуже.
- Роли `target-left / target-right / control` в тройке проб одной пары стоят по одному разу на A, B и C.
- **Контроль не бесплатен.** У контрольного варианта такая же реальная цена, как у вариантов пары. Раньше контролем часто был Индивидуалист с «покоем +3» и без потерь — безопасный выход, который игрок «на ресурсы» выбирал в 9 пробах из 21.
- **Точность иногда окупается.** Аккуратный вариант (часто Эксперт) не должен только платить: если в паре «Эксперт ↔ Достигатель» Эксперт всегда теряет больше всех, проба учит «не возиться». Хотя бы иногда тщательность приносит то, ради чего её выбирают: глазурь «пошла дороже», «спина отпустила».
- В каждом варианте пары должно читаться то, на чём проходит граница. Короткая шпаргалка по соседним границам (подробно — rubric §5):

| Пара | На чём граница | Не путать |
|---|---|---|
| Оппортунист ↔ Дипломат | своя выгода или защита сейчас — или добровольно уступаю ради своих и общего уговора | жёсткая граница ≠ Оппортунист, помощь ≠ Дипломат |
| Дипломат ↔ Эксперт | «так принято», «так сказал уважаемый» — или свой критерий качества и факта | спорность ≠ Эксперт |
| Эксперт ↔ Достигатель | правильно сделать свою часть — или добиться результата всего дела: приоритет, компромисс, поручить | Достигатель ≠ халтура |
| Достигатель ↔ Индивидуалист | дойти до цели — или усомниться в самой цели и мерке успеха | отказ от цели ≠ Индивидуалист |
| Индивидуалист ↔ Стратег | понять разные взгляды — или устроить порядок, который выдерживает эту разность | свод правил ≠ Стратег |
| Стратег ↔ Алхимик | выстроить гибкий порядок к нужному состоянию — или задать границы, внутри которых меняется сама рамка | бездействие ≠ Алхимик |
| Алхимик ↔ Ироничный | менять рамку — или спокойно не менять, если хватает простого способа | цинизм и отстранённость ≠ Ироничный |

### 6.4. Development (3 варианта)

- Варианты: **целевое событие бита** (`trial`, `consequence`, `review`, `transfer`, `pressure`), **отступление** (`withdrawal`, прежний способ) и **гибрид** без события развития.
- **Отступление — законный выбор**, а не провал: у прежнего способа есть настоящая выгода, текст его не высмеивает и не стыдит. Иначе дуга превращается в тест на «правильное» поведение.
- **Целевой вариант не привлекательнее остальных** и стоит реальной цены: новый способ действия даётся не бесплатно.
- **Гибрид честно неоднозначен:** из него нельзя понять, пошёл ли герой новым путём (пример пакета: «сначала вместе восстановить, как было» — может оказаться и честным разделом вины, и общим сокрытием).
- Целевой вариант не стоит почти всегда на одной позиции (rubric §16).

### 6.5. Сюжетные сцены

- Варианты могут вести в разные сферы (`servesFacets`), см. §3 и §8; логику не размечают.
- Те же правила цены и тона: ни один вариант не «правильный».

## 7. Различитель в метке: правка и подрезка

Метка варианта — это и есть то, по чему профиль читает логику. Сокращение, которое убрало слова одной компоненты вектора, меняет смысл, даже если вектор в данных остался прежним.

**Порядок при написании или сокращении метки:**

1. Открыть структуру: `content-src/v2.5/probes.json` (`neutral.json`, `development.json`). Прочитать у варианта исходный `text` пакета, `vector`, `lead` и `rationale` по шести осям.
2. Назвать ведущую и вторую компоненту (например, Стратег 0.65 / Эксперт 0.35) и найти в исходном тексте слова, которые несут каждую.
3. Сокращать только слова, которые не несут ни одной компоненты: обстоятельства, повторы, вводные.
4. Сравнить с соседними вариантами той же карточки: разница должна остаться видна без пояснений.
5. Если в ~55 символов не помещается, допустимо до 70. Лучше длиннее и точно, чем коротко и с потерянной логикой.
6. Пересобрать (`npm run v25:build`) и проверить, что дифф затрагивает только метки.

**Пример: `probe.alir.02`.** Сцена: обычный сырой черепок, причина известна, чинится по обычаю. Вариант `prevent-systemically` — Стратег 0.65 / Эксперт 0.35, в пакете: «исправить ошибку и встроить проверку, чтобы класс сбоев не зависел от человека».

| Метка | Что случилось |
|---|---|
| Исправлю и заведу проверку сырости, чтобы не от меня зависело (61) | исходная, всё на месте, но длинная |
| Заведу проверку сырости: пусть держится без меня (48) | ✗ выпало «исправлю»: пропала Эксперт-часть, стало хуже отличаться от `use-crisis` |
| Починю и заведу проверку сырости, чтобы не повторялось (54) | ✗ выпало «не зависит от человека»: пропала суть Стратега (порядок, который работает сам), осталась простая профилактика |
| **Починю и заведу проверку сырости — пусть держится без меня (58)** | ✓ починка (Эксперт) + порядок, работающий без героя (Стратег); «починю» — слово самой сцены |

Заодно соседний `fix-now` (Ироничный 0.65 / Эксперт 0.35) получил тот же глагол: «Починю известную причину по обычаю; смыслы — потом». Общая Эксперт-часть звучит одинаково, и разница между вариантами остаётся только там, где она есть в векторах.

Посмотреть метки рядом с векторами собранных карточек:

```bash
node -e 'for (const c of require("./src/content/data/cards.probe.json")) for (const x of c.choices) console.log(c.id, x.label.length, x.label, JSON.stringify(Object.fromEntries(Object.entries(x.diagnosticAction.vector).filter(([,v])=>v))))'
```

## 8. Как выглядит хорошая сюжетная карточка

```
Лия приезжает в мастерскую, когда Алексей заканчивает срочный заказ.
card.facets: [work, relationships]

A. Остаться и закончить заказ                    servesFacets: [work]
B. Отложить работу и поговорить с Лией           servesFacets: [relationships]
C. Договориться помочь друг другу                servesFacets: [work, relationships]
D. Признать, что сил уже нет                     servesFacets: [body]
```

`D` выходит за `card.facets` — это нормально.

## 9. Стиль текста

- Герой — «ты» (гончар). Алексей — ученик. Люди села: Марта, Тимон, Алексей, Егор, Лия, Странник, Фёкла (знахарка), Радим (костоправ и кузнец), Мирон (староста), Савва (старый мастер), Дарья (тётка), Ульяна (помощница).
- Текст сцены: 1–2 коротких фразы, до ~200 символов, конкретно, без пересказа чувств героя.
- Вариант: **до ~55 символов** (жёсткий предел 70), от первого лица, живым глаголом: «не отпущу», «промолчу», «подожду». Эмоция в интонации выбора, а не в оценке. Различитель важнее длины (§7).
- Отклик после выбора: 1–2 коротких фразы, телесный или бытовой след («Ты вздрагиваешь от каждого шага у ворот»), ≤ 280 символов, но в практике ≤ 100.
- Натуральные вещи вместо компьютерных: печь, глина, тетрадь Марты, дрова, колодец, ярмарка, повозка. Запрещены слова: приложение, экран, созвон, дедлайн, релиз, клиент, проект, бонус, KPI. Общий словарь замен — в `content-src/v2.5/skin/DRAFT-BATCH-0-sample.md`.
- Не оценивать варианты и не называть логики: слова «правильно», «мудро», «зрелый», «осознанный», «системный подход» ради выдачи поздней логики запрещены. Более поздняя логика не должна звучать как «лучший человек».
- Склонять имена по падежам: Фёкла, у Фёклы, Фёкле, Фёклу.
- Стоп-слова движка (`scripts/stoplist.ts`): бог, грех, святой, молитва, церковь, храм, рай, ад — не использовать.

## 10. Ресурсы и качества

- Ресурсы: достаток, силы, покой, близкие. Масштаб как в существующих карточках: ±1…6, редко больше. Ни один вариант не лучше остальных по всем ресурсам сразу; поздние логики не получают систематической выгоды (иначе ресурсы подсказывают «правильный» ответ).
- **Измеримо по пулу** (таблица линтера «ресурсы, качества и первое слово»): средняя сумма ресурсов на вариант у каждой логики — в пределах ±1.5 от средней по пулу; потери сопоставимы. Второй показатель — «выбор на ресурсы»: сколько карточек игрок, берущий вариант с наибольшей суммой ресурсов, отдаст каждой логике; ни одна логика не должна получать больше двойной честной доли. Честная доля — сколько карточек логика выигрывала бы, если бы ресурсы ничего не подсказывали: у логики, которая ведёт k из n вариантов карточки, это k/n. Для neutral (32 × 4, каждая логика по 16 вариантов) доля — 4; в пробах логики встречаются неравно, и доля у каждой своя (линтер печатает её в скобках). Если у какой-то логики варианты систематически дешевле и выгоднее, игрок, который играет «на ресурсы», будет выбирать её, и профиль прочтёт стратегию игры, а не способ действия.
- Качества (внимание, честность, сострадание, отпускание, смелость): в диагностических карточках только **+1** по смыслу варианта, без отрицательных и без привязки к логике. Без них половина слотов не растила бы качества и ломалась бы достижимость «теней». Измеримо: ни одна логика не получает больше половины всех +1 одного качества в пуле (например, не всё «сострадание» Дипломату и не всё «отпускание» Ироничному).
- `decisionKinds: ['cost']` — у варианта с потерей ≥ 3 в каком-либо ресурсе, и только у него. В скине его ставят вручную: при правке ресурсов пересчитать.
- **Отклик подтверждает ресурсы.** Если вариант стоит близких, в отклике кто-то обиделся или отдалился; если даёт достаток — видно, откуда деньги. Отклик не хвалит выбор устами персонажа («Мирон сказал, что правильно»): это подсказка «правильного» ответа.

## 11. Что нельзя трогать в диагностике и развитии

Векторы логик, порядок вариантов, `id` вариантов, роли (`left/right/control`), события развития и условия `requires` у карточек дуг берутся из пакета (`content-src/v2.5/*.json`) и при переписывании текста не меняются: так мир можно переписывать, не меняя математику. Сознательная правка влияния — отдельная работа, см. §0. Проверка `npm run check` сверяет собранные карточки с этими файлами.

Что не проверяет ни одна машина — и остаётся за человеком:
- сохранился ли различитель в метке (§7);
- вторые смыслы вариантов (не читается ли «правильный» ответ);
- слепая проверка редактором (κ ≥ 0.70, top-2 ≥ 90 %), особенно пара Алхимик ↔ Ироничный;
- соответствие `servesFacets` смыслу выбора в сюжетных сценах.

| Механическая проверка текстов | `npm run cards:lint` (`scripts/cards-lint.ts`) |

**Что проверяет машина.** `npm run content:check` — схему, сверку собранных карточек со структурой пакета и стоп-слова. `npm run cards:lint` — механическую часть §9 и §13:

| Уровень | Правило |
|---|---|
| ошибка | вариант (и вариант вопроса о мотиве) длиннее 70; слово из «компьютерного» списка §9 (приложение, клиент, проект, дедлайн, чат…); стоп-слово |
| предупреждение | вариант длиннее 55; сцена длиннее 200; отклик длиннее 100; разброс длины вариантов карточки больше 15; оценочное слово (правильно, мудро, зрелый, осознанный, разумный…); дословный повтор метки из другой карточки (neutral и probe); вариант, который лучше каждого другого варианта карточки по ресурсам (ни в одном не хуже, хотя бы в одном лучше) |
| таблицы | для neutral и probe: ведущая логика × сфера, баланс позиций, чья логика у самого длинного варианта (перекос, если у поздних логик больше 60 %); ресурсы, качества и частое первое слово по логикам (перекосы по §6.1 и §10 выписаны под таблицей); для дуг: позиция целевого события |

Ошибки ломают `npm run check` (там `cards:lint --strict --quiet`). Предупреждения не ломают: каждое читает человек и либо исправляет, либо оставляет осознанно. Например, «Отказать своему — неправильно» в вопросе о мотиве — собственные слова Дипломата, а не оценка автора. Списки слов и пределы — в начале `scripts/cards-lint.ts`; при пополнении §9 пополнять и их.

Смысл линтер не проверяет: сохранился ли различитель (§7), не читается ли «правильный» ответ, честны ли `servesFacets`.

## 13. Чек-лист перед сдачей карточки

**Для всех**
- [ ] Сцена: факт без психологии, настоящий компромисс, ≤ 200 символов (§5).
- [ ] Вариант ≤ 55 символов (максимум 70), отклик ≤ 100; разброс длины вариантов карточки не больше ~15 символов.
- [ ] Ни один вариант не написан привлекательнее; нет слов-оценок и подсказок «как правильно».
- [ ] Ранние варианты — изнутри: своя причина, цена фактом, без «только», «пусть», «втихую» (§6.1).
- [ ] Нет повтора формулировки из другой карточки; первое слово не повторяет шаблон своей логики.
- [ ] Каждый вариант описывает действие, а не угадываемый мотив.
- [ ] Только натуральные вещи, нет запрещённых слов, имена склонены.
- [ ] Нет варианта, лучшего по всем ресурсам; качества только +1 по смыслу.
- [ ] Четыре вопроса про сферы из §3 пройдены; сфера не привязана к одной логике в соседних карточках.

**Neutral и probe**
- [ ] Вектор, порядок, `id` и роли вариантов не тронуты.
- [ ] В каждой метке есть слова для каждой ненулевой компоненты вектора (§7); сверено с исходным `text` и `rationale`.
- [ ] Тема сцены не подсказывает логику (§5 п. 5); текст не зависит от стадии героя.
- [ ] Probe: два варианта видимо различают пару по её границе (§6.3), контроль правдоподобен.

**Development**
- [ ] Целевой вариант, отступление и гибрид на местах; события и `requires` из пакета не тронуты.
- [ ] Отступление законно и не высмеяно; целевой вариант стоит реальной цены; гибрид честно неоднозначен.

**Сюжет**

**Сборка**
- [ ] `npm run cards:lint -- --only <тип>`: ошибок 0, все предупреждения прочитаны (§14).

## 14. Порядок работы с каждой партией

Обязателен для каждой партии (проб, дуг, сюжетных сцен) и для любой правки текстов уже влитых карточек.

1. **Написать** тексты в `content-src/v2.5/skin/*.json` (или в `src/content/data/cards.*.json` для сюжета) по §5–§7. Для меток диагностики и развития — сверка с исходным `text`, `vector` и `rationale` пакета (§7).
2. **Собрать:** `npm run v25:build`.
3. **Линтер:** `npm run cards:lint -- --only <тип>` (`neutral`, `probe`, `development`, `story`).
   - ошибок должно быть 0;
   - каждое предупреждение прочитать: исправить или оставить осознанно;
   - посмотреть таблицы баланса: нет ли новой связки «сфера = логика», не стали ли поздние варианты длиннее, не дешевле ли и не выгоднее ли какая-то логика по ресурсам, не забирает ли она одно качество, нет ли у неё любимого первого слова, не съехало ли целевое событие дуги на одну позицию.
4. **Проверка целиком:** `npm run check` (контент, линтер, типы, тесты).
5. **Дифф:** `git diff --stat src/content/data` — меняется только то, что задумано (при правке текстов — только строки текстов).
6. **Человеческая часть чек-листа §13** — для каждой новой или изменённой карточки.
7. **После партии диагностики** — отметить карточки для повторной слепой проверки редактором (§11): её результат относится к конкретным формулировкам.
