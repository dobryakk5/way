## 2. `contentVersion`

Остаётся `mvp-v2.5-alpha.2`, список совместимых версий не менялся. Причины:

- Изменения контента аддитивны: старые сохранения остаются валидными без миграции (проверено выше).
- Сервер версию контента не читает (поиск `contentVersion` / `CONTENT_VERSION` по `server/src` — ни одного обращения), сопоставление идёт по идентификаторам сцен и выборов.
- Подъём версии без необходимости потребовал бы вносить текущую версию в `COMPATIBLE_CONTENT_VERSIONS` и затронул бы оценку накопленных данных профиля («evidence under a compatible version stays valid as written») — риск без выигрыша.
- Если владелец захочет метку релиза, безопасный путь — новая версия и **добавление** `mvp-v2.5-alpha.2` в список совместимых.

## 3. Политика «только добавление»

Серверные таблицы `scene_presentations` и `choice_presentations` append-only (триггеры), SQL каталога пишет ревизию 1 с `ON CONFLICT DO NOTHING`: отредактированный на месте текст **не попадает** на сервер, а клиент уже предъявил игроку новый текст. Сохранение замораживает предъявленные выборы (`state.current.choices`, при загрузке сравниваются с контентом канонически, включая эффекты; `impact` в сравнение не входит).

Следствие и правило (записано в `deploy/README.md`): опубликованный текст, вариант текста, подпись и предъявленная пара выборов не редактируются; новое — новый вариант текста (новый id) и `choiceVariants` с **новыми** id выборов. Правило проверяется `compat:snapshot` и тестом; «защита срабатывает» тоже тестируется (правка текста, подписи, эффекта, удаление варианта — ловятся; добавления — нет).

Из-за этого этап 3 переделан: первоначальные правки на месте (шесть сцен главы 2, `enc_*`) заменены аддитивными вариантами.

## 4. Точечное решение для `r_marta_hello/b`

Проблема: в опубликованной сборке выбор `b` «Договориться на вечер» ничего не планировал. Правка эффекта на месте сделала бы открытую в старом сохранении сцену невалидной (замороженная пара ≠ контент).

Решение без правок общей валидации:

1. Базовые выборы `a`/`b` карточки возвращены **ровно** к опубликованным (эффекты, подписи, порядок).
2. Новая развилка живёт в `choiceVariants` с условием `dayGte: 1` и **новыми** id `a2`/`b2`; `b2` планирует `r_marta_evening`.
3. Старое сохранение с открытой `r_marta_hello` содержит замороженные `a`/`b`; `applyChoice` использует замороженные выборы, поэтому игрок получает старые эффекты, а свежие показы получают новые.
4. Тест `appendOnlyContent.test.ts` («a scene that was already on the screen…») строит такое сохранение с опубликованной парой, валидирует его текущей `validateSave`, применяет `b` и проверяет старые эффекты; отдельно проверяется, что выбор не пересчитывается.

Покрытие сгенерированными сохранениями: `compat:old-saves` печатает, сколько сохранений имели на экране сцену, чьё содержимое изменилось. Сцен на экране было 144 разных; сохранений с изменившейся карточкой на экране — 525 (больше всего: `r_letter_stack` 50, `r_breakfast` 42, `r_customer_wait` 35, `r_market_price` 30, `r_evening_light` 26, `r_coins` 25, `r_sweep` 23, `r_river` 22, `r_kiln` 21, `enc_4_5` 21, `enc_4_0` 20, `enc_4_10` 14); все продолжены до конца. `r_marta_hello` в первую дюжину этого вывода не попала, поэтому её случай обязательно проверяется отдельным тестом выше, а не только массовым прогоном.

## 5. Старые сохранения

`scripts/compat-old-saves.sh`: во временном `git worktree` опубликованного коммита `ae8bad7` игра проигрывается 7 политиками, запись сохранения снимается каждые 6 решений и на каждой фазе (dice, slot, morning, evening, route, motive, chapter, intention, goal), затем текущая сборка:

- `validateSave`/`migrateSave` принимают запись;
- прохождение доигрывается до 120 решений, итоговое состояние валидно.

Результат: **1531 из 1531**. Фазы: dice 537, slot 807, morning 80, evening 71, route 6, motive 17, chapter 8, intention 3, goal 2.

Что нашла эта проверка: старый набор кубика с `r_letter_stack` (теперь с требованием `shown c1_liya_letter`) нельзя было бросить; `rollEncounter` теперь пересобирает такой набор (`prepareEncounter` на состоянии без последнего броска). Регрессия — тест «stale dice set».

### Обратное направление (новое сохранение → старый клиент)

Замерено отдельно: сохранения, записанные **текущей** сборкой (1515), загружаются **опубликованной** сборкой только в 320 случаях; остальные 1195 старый клиент считает повреждёнными. Это свойство любого добавления контента (в истории появляются id выборов и сцен, которых старая сборка не знает), а не дефект этой ветки. Практический смысл: **откат клиента на старую версию после выхода новой для игроков, успевших сыграть новое, ломает их сохранения.** Откатывать клиент нельзя; при проблеме — исправляющий релиз вперёд.

## 6. Каталог контента (сервер)

`scripts/compat-catalog.sh` (новый, на временном PostgreSQL 17, миграции 001–006): грузится каталог **опубликованной** сборки, затем **текущей** поверх.

| | |
|---|---|
| Опубликованный каталог | 234 сцены, 353 предъявления сцен, 622 выбора, 622 предъявления выборов |
| После загрузки текущего поверх | 243 сцены, 516 предъявлений сцен, 690 выборов, 690 предъявлений выборов |
| Опубликованные предъявления сцен / выборов | не изменились (контрольная сумма до и после совпала) |
| Правка текста на месте и повторная загрузка | в БД остаётся прежний текст (правка не сохраняется) — подтверждает необходимость политики «только добавление» |

Порядок выкладки (в `deploy/README.md`): **сначала загрузить каталог** (`npm run persistence:catalog`, SQL в `way_db`), затем `deploy.sh`: клиент сообщает серверу о встреченной сцене/выборе, а неизвестное сервер отклоняет (так сказано в `deploy/README.md`; конкретный код ответа не проверялся). Каталог — надмножество, поэтому старые клиенты после его загрузки продолжают работать.

## 7. Старый PWA и устаревшая вкладка

- Режим `registerType: 'autoUpdate'`: новый service worker подхватывается автоматически, precache — 47 файлов.
- Активной может быть одна вкладка (Web Lock `put-active-profile`, `acquireProfileLock`): устаревшая вкладка со старым клиентом не пишет одновременно с новой. Если старая вкладка держит блокировку, новая вкладка получает `onBlocked` и не пишет сохранение. Старый клиент пишет сохранения в прежнем формате, а текущая сборка их читает (раздел 5).
- Формат сохранения (`schema: 1`), `diceHistory`, структура `history`/`scheduled` не менялись.

## 8. Серверная синхронизация

- Сервер хранит события и предъявления по идентификаторам; новые сцены и выборы нужны ему в каталоге заранее (раздел 6).
- `contentVersion` сервер не читает.
- Старые идентификаторы и их тексты в каталоге не изменялись.

## 9. Что **не** проверено

- Реальное обновление PWA в браузере (новый service worker поверх старого, поведение вкладки при `autoUpdate`) — проверено только по коду и конфигурации.
- Живой API сервера: каталог проверен на PostgreSQL, но полный круг «новый клиент → эндпоинты синхронизации → БД» с реальным процессом `server/` не прогонялся.
- Пользовательские сохранения из реальных браузеров (IndexedDB), а не сгенерированные скриптом.
- Поведение при откате клиента — измерено на уровне валидатора (раздел 5), не в UI.

## 10. Остаточные риски

1. Откат клиента невозможен без потери сохранений тех, кто уже играл (раздел 5).
2. Нарушение порядка выкладки (клиент раньше каталога) приведёт к отказам синхронизации для новых сцен до загрузки каталога.
3. Любая будущая правка опубликованного текста «на месте» молча не дойдёт до сервера — защищает только `compat:snapshot` (входит в `npm run check`); после релиза снимок нужно обновить командой `npm run compat:snapshot -- --write`.
