# DEVELOPMENT-PRODUCTION-CARDS-v1
## «Путь»: production-карточки для 6 отсутствующих development arcs

**Статус:** контент готов; перед merge требуется привязка к фактической schema и существующим NPC/ресурсам репозитория.  
**Дата:** 5 октября 2026

## 0. Общий контракт

Все карточки ниже имеют `selectionOrigin = adaptive`. Они дают `DevelopmentEvidence`, но не являются profile-eligible диагностическими `neutral/probe` и не подтверждают `currentDistribution` или `observedPrimary`. Термин `independent` в старых runtime-полях означает именно eligibility источника, а не статистическую независимость.

Никакая карточка не меняет `developmentCurrent` напрямую. Promotion остаётся за существующим `developmentProgress()` и вечерним `commitDevelopmentPromotion()`.

Ролевые обозначения NPC:

- `npc.colleague.primary` — основной коллега Алексея;
- `npc.colleague.senior` — опытный/авторитетный коллега;
- `npc.manager.primary` — руководитель или заказчик;
- `npc.close.primary` — близкий человек;
- `npc.close.secondary` — друг/близкий знакомый;
- `npc.partner.primary` — партнёр по договорённости;
- `npc.specialist.primary/secondary` — два независимых специалиста/тренера;
- `npc.family.group` — семья/значимая группа;
- `npc.team`, `npc.team.a`, `npc.team.b` — команда/стороны конфликта;
- `npc.acquaintance.primary` — знакомый;
- `npc.authority.primary` — авторитетный внешний участник.

Перед merge эти ролевые ключи надо сопоставить с уже существующими персонажами истории. Не создавать дубль NPC, если соответствующая роль уже есть.

`worldEffectSpec` ниже — содержательное требование к эффекту мира. Конкретные `facts/resources/scheduled` поля должны использовать существующую runtime schema игры, а не новую параллельную схему.

Объём после reconciliation: **50 production-карточек** для шести новых arc: 36 основных карточек исходного пакета + 14 retry-support карточек, закрывающих ранние withdrawal. `expert → achiever` не переписывается, а проходит semantic audit.

## `dev.od.trial.01` — Чья это ошибка?

- function: `trial`
- facet: `work`
- contextId: `shared-responsibility`
- cast: `npc.colleague.primary`, `npc.manager.primary`

**Текст**

В совместной работе обнаружилась ошибка. Она возникла не из одного решения: Алексей пропустил важную проверку, а Коллега позже внёс изменение, после которого проблема проявилась. Руководитель спрашивает прямо: «Кто отвечал за этот участок?» Если Алексей отделит свою часть, основной удар почти наверняка придётся на Коллегу.

**Варианты**

1. `share_responsibility` — **Сказать, что ошибка сложилась из двух решений, и назвать свою часть ответственности.**  
   `developmentEvent: trial`  
   Смысл: добровольно принять цену ради взаимности.  
   worldEffectSpec: риск санкции для Алексея повышается; через 1–3 обычных решения открыть `dev.od.consequence.01`.

2. `protect_self` — **«После меня всё работало, дальше меняли без меня».**  
   `developmentEvent: withdrawal`  
   Смысл: непосредственная самозащита.  
   worldEffectSpec: руководитель переключает внимание на Коллегу; Алексей снижает личный риск, но доверие между ними ухудшается.

3. `coordinate_facts` — **Предложить сначала вместе восстановить последовательность действий и только потом отвечать.**  
   Без development evidence.  
   Смысл: гибрид; сам по себе не показывает, будет ли это честное распределение ответственности или совместное сокрытие.

# 8. Формальный retry-граф v1

`withdrawal` фиксирует не «проигрыш», а незавершённую попытку конкретного beat. Валидные evidence предыдущих beats не удаляются.

```text
withdrawal@trial
  → cooldown
  → retry-trial
  → trial evidence
  → consequence

withdrawal@consequence
  → cooldown
  → retry-consequence
  → consequence evidence
  → review

withdrawal@review
  → cooldown
  → retry-review
  → review evidence
  → transfer

withdrawal@transfer
  → cooldown
  → retry-transfer
  → transfer evidence
  → pressure

withdrawal@pressure
  → cooldown
  → существующая retry-card
  → pressure evidence
  → pendingPromotion
```

Cooldown одинаков для всех retry:

```text
1 завершённый вечер
OR
2 resolved non-arc choices
```

Правила:

1. Scheduler всегда ищет **первый обязательный beat без валидного evidence**.
2. Если для него записан withdrawal после последнего успешного evidence, обычная следующая карточка beat не показывается до cooldown.
3. После cooldown показывается карточка соответствующего `retry-*` типа.
4. Повторная карточка содержательно отличается от исходной; дословный replay запрещён.
5. `retry-trial` не позволяет перескочить к pressure.
6. `retry-pressure` может закрыть только pressure, если `trial + consequence + review + transfer` уже собраны.
7. Если в будущем автор добавляет withdrawal в consequence/review другой arc, content validator требует соответствующую `retry-consequence`/`retry-review` карточку.
8. В текущем пакете специальные ранние retry нужны для `OD review` и `DE consequence`; остальные consequence/review не создают withdrawal.
9. `withdrawal` и retry evidence идемпотентны по `(runId, arcId, cardId, choiceId)`.
10. Promotion всё равно происходит только на вечерней границе и только после полного набора beats.

# 9. Общие правила scheduling

Для всех шести новых arc:

```text
trial
→ 1–3 обычных решения
→ consequence
→ review
→ минимум 2 обычных решения ИЛИ смена дня
→ transfer
→ обычная жизнь
→ pressure
```

Не показывать пять development-карточек подряд.

После `withdrawal` повторная возможность не показывается немедленно. Минимальный cooldown:

```text
1 завершённый вечер
OR
2 resolved non-arc choices
```

Карточки `retry-*` закрывают тот beat, на котором произошёл withdrawal. Нельзя перескочить к `retry-pressure`, пока не собраны `trial + consequence + review + transfer`. Полная таблица маршрутов дана в разделе 8.

2. Каждый текстовый `worldEffectSpec` превращён в реальные эффекты мира: `facts/resources/scheduled/...`; последствия не остаются только литературным текстом.
3. У каждой arc достижим путь `trial → consequence → review → transfer → pressure`.
4. `transfer.contextId != trial.contextId`.
5. `pressure` содержит реальную цену, срочность, статусный риск или потерю контроля.
6. «Ложный зрелый» вариант никогда не даёт target `DevelopmentEvidence`.
7. `withdrawal` не удаляет ранее накопленные валидные evidence и не вызывает promotion.
8. Все arc-карточки остаются `adaptive`; они не входят в независимый `currentDistribution`.
9. Диагностические проценты не являются prerequisite для completion активной arc.
10. Promotion выполняется максимум один раз и только на вечерней границе.
11. После promotion следующая соседняя arc активируется только если реально существует.
12. Если следующей arc нет, календарь и обычная жизнь продолжаются.
13. Reload между любыми двумя beats не меняет уже записанное развитие.
14. Повторное применение той же choice-handler не дублирует `DevelopmentEvidence`.
15. `expert-achiever` остаётся зелёной по прежним четырём regression-сценариям.
16. Позиция target development-choice сбалансирована по пакету; content validator запрещает концентрацию target-choice на одной позиции.
17. Смысл choice привязан к `choiceId`, не к позиции; при runtime-shuffle порядок сохраняется через reload.

# 11. Что ещё требуется для буквального переноса в `cards.*.json`

Этот документ уже фиксирует тексты, choices, функции arc, `contextId`, грани и семантику `developmentEvent`. Он **не придумывает** точные имена ресурсов, фактов и полей действующего контента, потому что текущий `src.zip/scripts.zip` в этой ветке не предоставлен.

Перед финальным merge нужен короткий repo-binding этап:

1. сопоставить `npc.*` с реальными ID персонажей;
2. заменить `worldEffectSpec` на реальные `effects` текущей schema;
3. заменить текстовые `requires` на реальные conditions;
4. назначить день/окна доступности в реальном календаре;
5. проверить conflicts/capacity/mustShowBy/scheduled;
6. вставить карточки в существующие `cards.*.json`, не создавая отдельный runtime-формат;
7. прогнать `check-content`, development scenarios и полную симуляцию календаря.

После этого пакет можно включать в итоговое `IMPLEMENTATION-v2.5-DEVELOPMENT-CONTENT.md`.
